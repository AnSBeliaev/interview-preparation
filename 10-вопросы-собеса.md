Порядок как на собесе. Сначала статистика и оптимизация, потом ETL, Git, протоколы, JSON. В конце снова база: `EXPLAIN` и команды, которые просят написать. Практические команды по `users` и `orders` лежат в [11-sql-база.md](11-sql-база.md).

## Статистика PostgreSQL

`pg_stats` не устанавливают. Это готовое представление: обычная «таблица», которую база ведёт сама. Из неё читают, в неё не вставляют строки руками.

По каждой колонке каждой таблицы там лежит сводка, не сами данные. Сколько значений пустые, сколько разных значений, какие значения самые частые.

Смотреть так:

```sql
SELECT tablename, attname, null_frac, n_distinct, most_common_vals
FROM pg_stats
WHERE schemaname = 'public'
ORDER BY tablename, attname;
```

Имена колонок ответа всегда одни и те же. Меняются строки: одна строка описывает одну колонку одной таблицы.

- `tablename` — таблица.
- `attname` — колонка.
- `null_frac` — доля пустых. `0.67` значит «пусто примерно у двух строк из трёх».
- `n_distinct` — сколько разных значений. `-1` значит «все разные, и с ростом таблицы их станет больше». Отрицательная дробь вроде `-0.33` значит «разных значений примерно треть от числа строк».
- `most_common_vals` — самые частые значения. У кода страны это может быть `{RU}`.

Рядом в том же представлении есть ещё колонки. `most_common_freqs` — как часто встречаются значения из `most_common_vals`. `histogram_bounds` делит остальные значения на промежутки, по ним планировщик прикидывает диапазон вроде `price > 300`. Полный список на своей базе: `\d pg_stats`.

Пока сводку ни разу не собирали, этот `SELECT` вернёт ноль строк. Сводку пишет команда `ANALYZE`. Она не путать с `EXPLAIN ANALYZE`.

```sql
ANALYZE;
```

`ANALYZE` проходит по таблицам, считает сводку и записывает её. Строки `users` и `orders` она не печатает и не меняет. База отвечает одним словом `ANALYZE`. Обычно это делает фоновый процесс autovacuum. Вручную команду запускают, если в таблицу только что залили много строк и план стал врать: база ждала 10 строк, а прочитала 100000.

Если на собесе говорят «как установить pg_stats», ответ: представление уже есть, ставить его не нужно. Устанавливают другое расширение, `pg_stat_statements`. Оно помнит, какой запрос сколько раз выполнялся и сколько времени занял. Его включают в конфиге PostgreSQL и создают так:

```sql
CREATE EXTENSION pg_stat_statements;
```

### Как по этим цифрам решать, ускорять ли запрос

Запрос медленный, когда база читает слишком много строк. Ускорить его значит сделать так, чтобы она читала меньше.

Индекс — отдельный список для поиска. В книге по фамилии находят страницу, не читая всю книгу. В таблице по почте находят строку, не читая всех клиентов. За скорость поиска платят при записи: каждая новая строка попадает и в таблицу, и в этот список. Поэтому индекс вешают не на все колонки, а только там, где он реально отбрасывает лишние строки.

Цифры из `pg_stats` как раз отвечают на вопрос «отбросит или нет». Три ситуации на клиентах.

**Почти все значения одинаковые. Индекс не нужен.**

В сводке по `country_code` самое частое значение `{RU}`, и так помечены все три клиента. Представьте миллион клиентов, и почти у всех тоже `RU`. Запрос:

```sql
SELECT * FROM customers WHERE country_code = 'RU';
```

Он должен вернуть почти всю таблицу. Список для поиска тут не помогает: база всё равно прочитает почти всех. Индекс по `country_code` не создают. То же с `is_active`, если почти все активны. Запрос «покажи активных» почти ничего не отбрасывает.

**Все значения разные. На большой таблице индекс нужен.**

В сводке по `email` написано, что все почты разные. Запрос:

```sql
SELECT * FROM customers WHERE email = 'anna@example.com';
```

Из миллиона клиентов нужна одна строка. Без индекса база читает миллион. С индексом по `email` она открывает список и сразу берёт эту строку. Индекс здесь оправдан. Так же ищут заказы одного клиента по `orders.customer_id`: у одного человека заказов мало по сравнению со всей таблицей.

**Цифры врут, потому что их давно не обновляли. Сначала обновить цифры, не индекс.**

`pg_stats` заполняет команда `ANALYZE`. Если после неё в таблицу залили миллион строк, а `ANALYZE` не запускали, в сводке всё ещё написано «клиентов трое». База верит сводке и выбирает способ чтения для трёх строк. На миллионе этот способ оказывается медленным.

Сначала снова выполняют `ANALYZE`. Потом ещё раз смотрят запрос. Часто этого достаточно, и индекс не нужен. Индекс по старым цифрам легко добавить зря.

На ваших трёх клиентах и трёх заказах разницы во времени не будет в любом случае. Три строки прочитать быстрее, чем открывать отдельный список. Решение «вешать индекс» принимают, когда строк много, а условие оставляет мало.

Коротко, что сказать на собесе. Смотрю колонку из `WHERE` в `pg_stats`. Если это значение почти у всех, индекс не создаю. Если все значения разные и таблица большая, создаю. Если цифры старые, сначала `ANALYZE`.

## Индексы

Подробный разбор с нуля: [12-индексы.md](12-индексы.md). Ниже только имена, чтобы не потерять место в этом файле.

На этом собесе называют два.

**B-tree** стоит по умолчанию, слово `USING btree` можно не писать. Он обслуживает равенство, сравнение, `BETWEEN`, `IN`, сортировку и префикс `LIKE 'abc%'`. Поиск `LIKE '%чай'` по нему не идёт: процент в начале означает, что начало строки неизвестно.

Индекс не вешают на каждую колонку. Он ускоряет чтение по условию и замедляет вставку: индекс тоже надо обновить. Бесполезен флаг, который почти у всех `true`: условие ничего не отсекает, планировщик читает таблицу.

```sql
CREATE INDEX orders_customer_id_idx ON orders (customer_id);
```

**GIN** нужен для `jsonb`. Он ищет ключ внутри документа, а не сравнивает документ целиком. Оператор такой проверки — `@>`.

```sql
CREATE INDEX products_attrs_gin ON products USING gin (attrs);
```

Фраза: «Обычный фильтр, диапазон и сортировка — B-tree. Поиск ключа внутри JSONB — GIN и `@>`. Индекс вешаю на колонку, по которой реально отсекаются строки».

## ETL и ELT

Оба слова про путь данных из источника в хранилище. Буквы одни, порядок T и L разный.

ETL: забрали, преобразовали отдельным скриптом, в базу положили уже готовый результат. Так делают, когда сырьё грязное или персональные данные нельзя грузить как есть.

ELT: забрали, положили сырьё в хранилище, преобразовали уже SQL внутри него. Так делают, когда само хранилище считает большой объём быстрее внешнего скрипта.

Фраза: «ETL меняет до загрузки. ELT сначала грузит сырьё, потом меняет его SQL внутри хранилища».

## Git

### Коммит

Коммит фиксирует уже отобранные файлы. Сначала `git add`, потом `git commit`.

```powershell
git add .
git commit -m "feat: add paid orders query"
```

Один коммит — одна правка. Префикс говорит вид: `feat` новая возможность, `fix` починка, `perf` скорость, `refactor` перестройка без нового поведения.

### Длинный комментарий

Заголовок — до 50 символов. Потом пустая строка. Потом текст: зачем сделано. Второй `-m` становится этим текстом, пустую строку Git ставит сам.

```powershell
git commit -m "feat: add paid orders query" -m "Join orders to customers and keep only paid rows."
```

Без `-m` откроется редактор. Первая строка — заголовок, затем пустая строка, затем пояснение.

### Конфликт слияния

Конфликт возникает, когда две ветки поменяли одни и те же строки. Git не выбирает сторону сам и оставляет в файле маркеры.

```text
<<<<<<< HEAD
своя версия
=======
входящая версия
>>>>>>> feature/branch
```

До `=======` текущая ветка. После него входящая. Маркеры кодом не являются. Их удаляют, оставляют нужные строки, затем `git add` и `git commit`. Пока конфликт не разобран, `git status` пишет `unmerged`.

### IDE

В VS Code, Cursor, WebStorm, PhpStorm и PyCharm это одно и то же трёхстороннее окно. Слева текущая версия, справа входящая, по центру итог.

Кнопки называются по-разному, действие одно.

- Accept Current, Accept Yours, Accept Left — взять свою сторону целиком.
- Accept Incoming, Accept Theirs, Accept Right — взять входящую сторону целиком.
- Accept Both — оставить оба куска друг за другом. Лишнее потом удаляют руками.

Кнопка не заменяет чтение. После неё в файле не должно остаться маркеров `<<<<<<<`. Дальше тот же `git add` и коммит.

### cherry-pick

`cherry-pick` берёт один коммит и заново применяет его на текущей ветке. Получается новый коммит с новым хешем. Старый коммит на своей ветке остаётся.

Зачем: длинная ветка ещё не готова к слиянию, а один коммит из неё нужен в `main` сейчас.

```powershell
git switch main
git cherry-pick c3a4f12
```

Если то же место на `main` уже другое, cherry-pick останавливается на конфликте. Разбор тот же: маркеры, `git add`, затем `git cherry-pick --continue`. Бросить попытку: `git cherry-pick --abort`.

Фраза: «Коммит — `git add` и `git commit`. Длинное сообщение — заголовок и тело через второй `-m`. Конфликт разбираю в окне IDE: слева своё, справа входящее, по центру итог, маркеры удаляю. `cherry-pick` переносит один коммит на текущую ветку новым хешем».

## WebSocket и gRPC

WebSocket — постоянное соединение браузера с сервером. Начинается как обычный HTTP, затем остаётся открытым. Обе стороны шлют сообщения в любой момент. Берут для чата, уведомлений, живого обновления экрана. Сообщения чаще в JSON.

gRPC — вызов метода другого сервиса. Контракт записан в файле `.proto`: имя метода, типы аргументов и ответа. Данные бинарные, соединение по HTTP/2. Берут между бэкендами, когда вызовов много и схема обязана совпадать. Браузер напрямую им обычно не пользуется.

Фраза: «Браузеру для живого потока — WebSocket. Между сервисами со строгим контрактом — gRPC».

## JSON, XML и типы

JSON — обычный формат своих API и веба. XML оставляют, когда формат уже навязан другой стороной: банк, государство, документ с подписью. «Что лучше» зависит от стороны. Свой сервис — JSON: его проще читать и он меньше весит. Чужой шлюз со схемой — XML, пока другая сторона не согласилась на JSON.

Схема XML называется XSD. Это отдельный файл: какие теги разрешены, в каком порядке, какие поля обязательны. Файл, который схеме не соответствует, принимающая сторона отвергает.

Тип данных говорит, какое значение лежит в поле и что с ним можно делать. У JSON шесть типов: строка, число, логическое значение, массив, объект и `null`. Отдельного типа «дата» нет. Дату передают строкой `2026-10-26`. Отдельного типа «файл» нет. Байты передают строкой Base64. В XML типы задаёт XSD: там бывают и строка, и число, и дата.

Фраза: «Свой API — JSON. XML, когда схему дала другая сторона, эта схема называется XSD. В JSON шесть типов, даты и байтов среди них нет».

## EXPLAIN и EXPLAIN ANALYZE

Это второй заход про оптимизацию. Сначала смотрели сводку по колонкам. Здесь смотрят план одного конкретного запроса: как база собирается его выполнить.

Обе команды пишутся перед обычным `SELECT`. Сам `SELECT` при этом остаётся прежним.

```sql
EXPLAIN
SELECT * FROM orders WHERE customer_id = 1;
```

`EXPLAIN` запрос не выполняет и строки заказов не показывает. Он печатает план: оценку, сколько это будет стоить и сколько строк база ожидает увидеть. Оценку она берёт из `pg_stats`.

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 1;
```

`EXPLAIN ANALYZE` план выполняет по-настоящему. К оценке добавляется факт: сколько миллисекунд заняло и сколько строк реально прочитано. Слово `ANALYZE` здесь — режим команды `EXPLAIN`. Это не команда `ANALYZE`, которая собирает статистику в `pg_stats`. Одинаковое слово, два разных действия.

Запрос с `INSERT`, `UPDATE` или `DELETE` под `EXPLAIN ANALYZE` тоже выполнится. Для учебной проверки таких команд перед ним ставят `BEGIN`, а после просмотра плана `ROLLBACK`, чтобы запись откатилась. На `SELECT` откат не нужен: чтение таблицу не меняет.

### Как читать строку плана

Ответ выглядит примерно так. Числа на вашей базе будут другими. Важна форма строки.

```text
Seq Scan on orders  (cost=0.00..1.04 rows=2 width=72) (actual time=0.015..0.018 rows=2 loops=1)
  Filter: (customer_id = 1)
  Rows Removed by Filter: 1
Planning Time: 0.080 ms
Execution Time: 0.045 ms
```

Слева направо.

`Seq Scan on orders` — последовательное чтение. База идёт по таблице `orders` от начала к концу и смотрит каждую строку. Индекс в этом плане не используется.

`cost=0.00..1.04` — оценка стоимости в условных единицах планировщика, не в миллисекундах и не в рублях. Число до двух точек — стоимость, чтобы выдать первую строку. Число после — стоимость всего результата. Сравнивать эти числа можно только внутри одного плана: у какого способа число меньше, тот планировщик считает дешевле.

`rows=2` до скобки `actual time` — сколько строк база ожидала. Это прогноз из статистики.

`width=72` — ожидаемая средняя длина одной строки ответа в байтах.

`actual time=0.015..0.018` — факт в миллисекундах. До двух точек — когда пришла первая строка. После — когда результат был готов.

`rows=2` внутри скобки с `actual time` — сколько строк получилось на самом деле. Это число сравнивают с прогнозом `rows` снаружи. Если прогноз 2, а факт 2, сводка попала. Если прогноз 10, а факт 100000, статистика устарела: сначала `ANALYZE`, и только потом вывод про индекс.

`loops=1` — этот шаг выполнился один раз. В соединении большой таблицы с маленькой шаг может выполниться много раз, тогда время в `actual time` показано за один проход, а полное время примерно в `loops` раз больше.

`Filter: (customer_id = 1)` — условие, которым база отбрасывает строки уже после чтения. `Rows Removed by Filter: 1` — одна строка прочитана и выброшена. На большой таблице много выброшенных строк при `Seq Scan` значит, что условие избирательное, а индекса по нему нет.

`Planning Time` — сколько заняло составить план. `Execution Time` — сколько заняло выполнить запрос. На собесе смотрят на выполнение и на число строк, не на сотые доли миллисекунды учебной таблицы.

### Какое чтение бывает в плане

`Seq Scan` — вся таблица подряд. Для трёх заказов это нормальный выбор: открыть индекс дороже, чем прочитать три строки. Это не ошибка схемы.

`Index Scan` — база идёт по индексу и достаёт подходящие строки. Условие в плане называется `Index Cond`, не `Filter`: отбор случился в индексе, лишние строки таблицы не читались.

`Bitmap Index Scan` — по индексу сначала собирается список подходящих мест в таблице, затем эти места читаются. Тоже использование индекса. Его выбирают, когда подходящих строк много, но всё ещё не почти вся таблица.

Решение после плана такое.

- Прогноз `rows` и факт `rows` сильно разошлись. Обновить статистику командой `ANALYZE` и снять план ещё раз.
- На большой таблице `Seq Scan`, а `Rows Removed by Filter` огромный. Условие отсекает мало строк. Имеет смысл индекс, для обычной колонки это B-tree.
- `Index Scan` есть, но условие почти ничего не отсекает. Индекс читается зря. Для флага, который почти у всех `true`, так и будет.
- Таблица маленькая, `Seq Scan` и время крошечное. Индекс не добавляют: выигрыша нет.

Фраза: «`EXPLAIN` показывает план и ничего не выполняет. `EXPLAIN ANALYZE` выполняет и пишет факт: `actual time` в миллисекундах и `rows` сколько строк вышло. Эти `rows` сравниваю с прогнозом. Если прогноз врёт, сначала `ANALYZE`. Если на большой таблице `Seq Scan` выбрасывает почти все строки, добавляю B-tree».

## Команды SQL, которые просят написать

Их пишут руками. Подробный разбор с таблицей `users` — в [11-sql-база.md](11-sql-база.md). Здесь то, что сказать, если попросят смысл.

`CREATE TABLE` создаёт таблицу и задаёт колонки. Строк после неё ещё нет. У колонки есть имя, тип и правила: `NOT NULL`, `UNIQUE`, `DEFAULT`, `PRIMARY KEY`.

`ALTER TABLE` меняет уже существующую таблицу. `ADD COLUMN` добавляет колонку, у старых строк она пустая, если не задан `DEFAULT`. `ALTER COLUMN ... TYPE` меняет тип, команда проходит, только если старые значения влезают. `RENAME COLUMN` меняет имя. `DROP COLUMN` удаляет колонку вместе со значениями. `SET DEFAULT` задаёт значение для будущих вставок и не заполняет уже лежащие пустые клетки. `ADD CONSTRAINT` вешает правило: внешний ключ или `CHECK`.

`WHERE` оставляет строки до группировки. `AND` требует оба условия. `IN` проверяет список. Пустоту ищут через `IS NULL`, запись `= NULL` не находит строк. `LIKE 'user_1%'` — текст с таким началом, `%` значит любой хвост.

`BETWEEN` включает обе границы. Для дат с временем граница `2026-01-31` — это полночь, остаток дня 31 января в диапазон не входит. День целиком пишут так: `created_at >= '2026-01-01' AND created_at < '2026-02-01'`.

`ORDER BY` сортирует уже отобранные строки. `DESC` — по убыванию. `LIMIT` берёт верхние n после сортировки. `NULLS LAST` отправляет пустые значения в конец.

Подробный разбор `JOIN` с нуля: [13-join.md](13-join.md).

`JOIN` ставит строку одной таблицы рядом со строкой другой, если условие `ON` сошлось. В ответе только пары. `LEFT JOIN` оставляет все строки левой таблицы. Пары нет — колонки правой пустые, `NULL`. `RIGHT JOIN` оставляет правую сторону, на практике пишут `LEFT`, поменяв таблицы местами. `FULL JOIN` оставляет обе стороны. `CROSS JOIN` клеит каждую строку с каждой, условия `ON` нет.

`GROUP BY` схлопывает строки с одинаковым значением в одну кучку. `count`, `sum`, `avg` считают внутри кучки. Всё, что в `SELECT` написано без этих функций, стоит в `GROUP BY`. `HAVING` выкидывает уже готовые кучки. `sum` в `WHERE` писать нельзя: суммы к этому шагу ещё нет.

Порядок смысла: `FROM` → `JOIN` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY` → `LIMIT`. Псевдоним из `SELECT` в `WHERE` не виден, в `ORDER BY` виден.
