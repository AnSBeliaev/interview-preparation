# Суббота. Типы PostgreSQL и DDL

Диалект весь день один: PostgreSQL. Колонку читают так:

```sql
имя  тип  [NOT NULL]  [DEFAULT выражение]  [остальные ограничения]
```

Квадратные скобки в эту строку не печатают. Так в учебниках помечают кусок, который можно не писать. Обязательны только имя и тип. Остальное добавляют, когда для колонки есть правило.

Готовая строка колонки выглядит так:

```sql
is_active boolean NOT NULL DEFAULT true
```

`is_active` — имя. `boolean` — тип. `NOT NULL` — пустым оставить нельзя. `DEFAULT true` — если при добавлении строки колонку не передали, база сама запишет `true`.

`DEFAULT` срабатывает только в этот момент, при `INSERT`, и только если значение не пришло. Позже оно само не обновляется. После `DEFAULT` пишут выражение, то есть то, что база умеет вычислить:

- число, текст или флаг: `DEFAULT 0`, `DEFAULT 'RU'`, `DEFAULT true`;
- текущий момент: `DEFAULT now()`;
- случайный идентификатор: `DEFAULT gen_random_uuid()`;
- пустой JSON: `DEFAULT '{}'::jsonb`.

Текст в выражении берут в одинарные кавычки. `true`, числа и вызовы функций вроде `now()` пишут без кавычек.

«Остальные ограничения» — это ещё три правила, их ставят в конец той же строки:

- `UNIQUE` — такое значение во всей таблице встречается один раз: `email varchar(320) NOT NULL UNIQUE`.
- `CHECK (условие)` — строка обязана проходить условие: `price numeric(12, 2) NOT NULL CHECK (price >= 0)`.
- `REFERENCES таблица (колонка)` — это ссылка на другую таблицу. Так объявляют внешний ключ: `customer_id bigint NOT NULL REFERENCES customers (id)`.

`PRIMARY KEY` тоже пишут в конце строки. Это не номер и не тип. Это правило: по значению в этой колонке находится ровно одна строка. Значение не бывает пустым и не повторяется. Чаще всего так помечают колонку `id` с числами 1, 2, 3. Но главным может быть и не число: например, почта в таблице клиентов, если двух одинаковых почт быть не может.

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

Строки в SQL пишут в одинарных кавычках: `'paid'`. Двойные кавычки обозначают имя, не текст. `NULL` пишут без кавычек. Пустая строка `''` и `NULL` — разные вещи: пустая строка есть, `NULL` значит «значения нет».

Дальше идут типы. У каждого один и тот же порядок: что это, готовая строка, разобранная слово за словом, какую фразу сказать на собесе.

## Целые

Целое число — это 1, 20, −3, без дробной части. Для целых в PostgreSQL три типа. Отличаются они только тем, какое самое большое число влезает.

| Тип | Какое число влезает | Куда писать |
| --- | --- | --- |
| `smallint` | примерно до 32 тысяч | маленький счётчик, остаток на складе в учебном магазине |
| `integer` | примерно до 2 миллиардов | обычное количество, номер товара |
| `bigint` | гораздо больше 2 миллиардов | номер клиента, номер заказа |

Байты и точные границы на собесе не спрашивают. Достаточно знать: `smallint` маленький, `integer` обычный, `bigint` берут для номеров, которые могут вырасти на годы вперёд.

Три готовые строки:

```sql
stock smallint NOT NULL DEFAULT 0
qty integer NOT NULL
customer_id bigint NOT NULL
```

Первая строка, слово за словом. `stock` — имя, «остаток». `smallint` — тип, маленькое целое. `NOT NULL` — пустым остаток не бывает. `DEFAULT 0` — если остаток не передали, запишется ноль.

Вторая. `qty` — количество штук в заказе. `integer` — обычное целое. `NOT NULL` — количество обязательно. Значения по умолчанию нет: если штуки не передали, база строку не примет.

Третья. `customer_id` — номер клиента, на которого ссылается заказ. `bigint` — большое целое, потому что это номер, а номера копятся. `NOT NULL` — заказ без клиента не записывают.

Фраза: «Остаток на складе влезет в `smallint` или `integer`. Номер заказа беру `bigint`, чтобы не упереться в два миллиарда».

## Дробные и деньги

Дробное число — это цена `1990.50` или вес `1.2`. Здесь развилка: точная дробь или приблизительная.

| Тип | Что лежит внутри | Когда брать |
| --- | --- | --- |
| `numeric(p, s)` | десятичная дробь без ошибки округления | деньги, всё, что считают в копейках |
| `real` | приблизительное число, покороче | вес, где десятая грамма не важна |
| `double precision` | такое же приблизительное, только длиннее | рейтинг, измерение, научный расчёт |

`numeric` и `decimal` в PostgreSQL — два имени одного типа. Пишите `numeric`.

Скобки `numeric(12, 2)` читают так. `12` — сколько цифр всего. `2` — сколько из них после запятой. Влезает число вроде `9999999999.99`: десять цифр до запятой и две после, вместе двенадцать.

Готовые строки:

```sql
price numeric(12, 2) NOT NULL CHECK (price >= 0)
weight_kg real
rating double precision
```

Первая строка, слово за словом. `price` — цена. `numeric(12, 2)` — точные деньги с двумя знаками после запятой. `NOT NULL` — цена обязательна. `CHECK (price >= 0)` — база отвергнет строку, если цена меньше нуля. `CHECK` — это ограничение из начала файла.

Вторая. `weight_kg` — вес в килограммах. `real` — приблизительный тип. Правил нет: вес можно не указать, отрицательное значение эта строка тоже пропустит. Для учёбы так и задумано, чтобы было с чем сравнить цену.

Третья. `rating` — рейтинг. `double precision` — приблизительный тип подлиннее. Тоже без правил.

Почему цена — `numeric(12, 2)`, а не `real`. Цена — это рубли и копейки. `1990.50` должно так и остаться: 1990 рублей и 50 копеек. `real` хранит дробь приблизительно. Для компьютера `0.1` в этом типе не ровно одна десятая, и в сумме появляется хвост вроде `0.30000000000000004` вместо `0.30`. На одном ценнике хвост не виден. На тысяче платежей он складывается в лишние или пропавшие копейки, и отчёт расходится с кассой. `numeric(12, 2)` хранит сами десятичные цифры: всего до 12 цифр, из них 2 после запятой, то есть как раз копейки. Вес чайника в `real` допустим: `1.2000001` кг вместо `1.2` кг никому не мешает. С деньгами так нельзя.

Проверка делается в том чёрном окне, где строка начинается с `postgres=#`. Это и есть `psql`: программа, в которой вы пишете команды для базы. Вы его уже открыли командой `docker exec -it pg psql -U postgres`. Пока на экране `postgres=#`, новое окно запускать не нужно. Две команды ниже вставляют по очереди, каждую заканчивают точкой с запятой и нажимают Enter.

Если чёрное окно закрыто или снова виден обычный PowerShell (`PS C:\...>`), `psql` надо открыть заново той же командой `docker exec`. Пока вы внутри `psql`, PowerShell команды не слышит.

```sql
SELECT 0.1::float4 + 0.2::float4;
SELECT 0.1::float8 + 0.2::float8;
SELECT 0.1::numeric + 0.2::numeric;
```

`SELECT` — это команда, не оператор. Оператор в этой строке — плюс: он складывает. `SELECT` стоит в начале и значит «посчитай то, что дальше, и покажи мне результат». Таблицу он не меняет. `CREATE` и `ALTER` меняют устройство таблицы, `SELECT` только читает и выводит.

Двоеточие с типом, `::float4`, значит «считай это число таким типом». Слова `real` в команде нет: у `real` в этой записи внутреннее имя `float4`. У `double precision` внутреннее имя `float8`. Оба приблизительные, поэтому хвост появляется и там, и там. `numeric` — точный тип для денег, у него хвоста нет.

Плюс складывает. У `float4` и `float8` сумма часто выходит с хвостом, например `0.30000000000000004`, а не `0.30`. У `numeric` выходит ровно `0.3`.

Фраза: «Цена — `numeric(12, 2)`. Вес могу положить в `real`, потому что десятая грамма здесь не деньги».

## Строки

Строка — это текст: имя, email, код страны. Три типа отличаются тем, что база делает с длиной.

| Тип | Что сделает база |
| --- | --- |
| `varchar(n)` | примет текст не длиннее n символов |
| `text` | примет текст любой длины |
| `char(n)` | дополнит текст пробелами ровно до n символов |

`n` в скобках — число, которое подставляете вы. `varchar(320)` значит «не длиннее 320 символов».

Готовые строки:

```sql
email varchar(320) NOT NULL
full_name text NOT NULL
country_code char(2) NOT NULL DEFAULT 'RU'
```

Первая. `email` — почта. `varchar(320)` — текст с потолком 320. `NOT NULL` — без почты клиента не создают. Потолок здесь не из-за скорости, а потому что у почты есть разумный предел.

Вторая. `full_name` — имя человека. `text` — текст без потолка: имена бывают длинные, заранее резать их незачем. `NOT NULL` — имя обязательно.

Третья. `country_code` — код страны. `char(2)` — ровно два символа. `NOT NULL` — код обязателен. `DEFAULT 'RU'` — если код не передали, запишется `RU`. Кавычки одинарные, потому что `RU` — текст.

Пробелов в `'RU'` нет, и это нормально. Букв уже две, а `char(2)` требует ровно два символа. Добавлять нечего. Пробел появляется только когда букв меньше, чем `n`. Одна буква `R` в `char(2)` хранится как буква `R` и пробел после неё.

Обычная функция `length` этот пробел не считает. Поэтому запрос

```sql
SELECT length('R'::char(2));
```

возвращает `1`, хотя внутри лежат два символа. Так устроена именно функция `length` для типа `char`, это не ошибка ввода.

Увидеть, что пробел всё же хранится, можно так:

```sql
SELECT octet_length('R'::char(2));
SELECT encode('R'::char(2)::bytea, 'escape');
```

Первая команда вернёт `2`: занято два байта, буква и пробел. Вторая покажет `R` и пробел после неё. Для `'RU'` дополнять нечем, там обе позиции заняты буквами.

Этот невидимый пробел потом мешает. Поэтому `char` почти не используют. Код страны спокойно пишут и как `varchar(2)`. В учебной таблице стоит `char(2)`, чтобы тип один раз встретился.

`varchar` и `text` в PostgreSQL работают одинаково быстро. Выбирают не по скорости. Есть деловой предел длины — `varchar(n)`. Предела нет — `text`.

Фраза: «`varchar(n)` ограничивает длину, `text` не ограничивает, по скорости в Postgres они равны. `char(n)` добивает значение пробелами до ровно n символов».

## boolean

`boolean` — колонка-переключатель. В ней два рабочих значения: `true` (да) и `false` (нет). Это не число `1` и не текст `'true'`.

```sql
is_active boolean NOT NULL DEFAULT true
```

Эту строку вы уже разобрали в начале: имя, тип, пустым не бывает, если не передали — запишется `true`.

Зачем вместе `NOT NULL` и `DEFAULT`. Без `NOT NULL` у переключателя появляется третье состояние, `NULL`: не «да» и не «нет», а «неизвестно». Для «клиент активен» так обычно не делают. Хотят именно да или нет, поэтому запрещают пустоту и задают запасное значение.

Если написать только `is_active boolean NOT NULL`, без `DEFAULT`, и при добавлении строки значение не передать, строка не запишется. База вернёт ошибку: колонка обязательна, а подставить ей нечего. То же будет, если передать `NULL`. Строка запишется, только если в команде явно указано `true` или `false`. `DEFAULT` как раз избавляет от этой ошибки: значение можно не передавать, база сама поставит `true`.

Фраза: «Флаг — это `boolean`, не ноль и единица. Если он обязателен, ставлю `NOT NULL` и `DEFAULT`».

## Дата и время

Четыре типа. Путают обычно два последних.

| Тип | Что лежит в ячейке | Пример значения |
| --- | --- | --- |
| `date` | календарный день, без часов | `1994-04-12` |
| `time` | часы и минуты, без дня | `10:30` |
| `timestamp` | день и часы, пояс не запоминается | `2026-10-25 12:00:00` |
| `timestamptz` | конкретный момент | тот же полдень, но база знает, по каким часам |

Пояс — это «московское время» или «время по Гринвичу». Одни и те же цифры `12:00` в Москве и в Лондоне — разные моменты.

`timestamp` хранит цифры как их написали и не помнит, чьи это часы. Два сервера в разных городах могут записать `12:00` и иметь в виду разное.

`timestamptz` хранит сам момент. Когда вы смотрите значение, база показывает его в поясе вашего подключения. В справочнике типов полное имя — `timestamp with time zone`. В командах пишут короткое `timestamptz`.

Готовые строки:

```sql
birth_date date
delivery_slot time
ordered_at timestamp NOT NULL DEFAULT now()
created_at timestamptz NOT NULL DEFAULT now()
```

Первая. `birth_date` — день рождения. `date` — только день. Часы рождения в этой колонке не хранят. Пустым день может быть: ограничения нет.

Вторая. `delivery_slot` — во сколько привезти, например `10:30`. `time` — только время суток, без даты. Тоже можно не заполнять.

Третья. `ordered_at` — день и часы заказа без пояса. `NOT NULL` — время заказа обязательно. `DEFAULT now()` — если его не передали, база подставит текущий момент. `now()` — функция, скобки пишут обязательно, кавычек вокруг нет.

Четвёртая. `created_at` — когда строка появилась в системе. Тип уже `timestamptz`: это момент, а не местные цифры. Остальное то же: обязательно и по умолчанию `now()`.

`now()` само по себе возвращает момент с поясом. Если колонка объявлена как `timestamp`, база переведёт этот момент в часы вашего подключения и пояс отрежет. Поэтому для «когда это случилось в системе» колонку сразу объявляют `timestamptz`, а не надеются на перевод.

Фраза: «`timestamp` — цифры даты и часов без пояса. `timestamptz` — конкретный момент. События системы пишу в `timestamptz`».

## uuid

`id` и `uuid` — не одно и то же. `id` — это имя колонки и её роль: «номер этой строки». Тип у номера бывает разный. `id bigint` хранит короткие номера `1`, `2`, `3`. `id uuid` хранит длинный номер особого вида. Слово `uuid` само по себе не значит «это и есть id». Это название типа, как `integer` или `text`.

`uuid` — длинный номер фиксированного вида, например `6f9619ff-8b86-d011-b42d-00cf4fc964ff`. Его не считают по порядку, как 1, 2, 3. Его генерируют так, чтобы он почти наверняка не совпал с другим даже в другой базе.

```sql
external_id uuid NOT NULL DEFAULT gen_random_uuid()
```

Каждое слово строки выше: `external_id` — внешний номер. `uuid` — тип. `NOT NULL` — номер обязателен. `DEFAULT gen_random_uuid()` — если номер не передали, база сама соберёт новый. `gen_random_uuid` — имя функции, скобки пустые, потому что ей ничего не передают.

Зачем тогда вообще `bigint`, если есть `uuid`. В одном магазине и одной базе заказы спокойно нумеруют `1`, `2`, `3`. Такой номер — это `bigint`. Он короткий, и по нему видно, какой заказ был раньше: `15` появился позже, чем `14`. Счётчик живёт внутри этой базы и выдаёт следующее число сам.

`uuid` нужен, когда одного общего счётчика нет. Например, номер заказа придумывает чужая программа ещё до записи в нашу базу. Или заказы одновременно создают две разные базы, и у каждой свой счётчик с единицы: обе выдадут номер `1`, и номера столкнутся. Длинный случайный `uuid` почти наверняка не повторится, даже если его придумали в разных местах и не спрашивали друг друга.

Готовое значение `uuid` в команде пишут текстом в одинарных кавычках:

```sql
'6f9619ff-8b86-d011-b42d-00cf4fc964ff'
```

Фраза: «Свой счётчик — `bigint`. `uuid` — когда номер приходит извне или его нельзя выдать по порядку в одной базе».

## json и jsonb

JSON — текст с данными в фигурных скобках: `{"color": "red", "volume_l": 1.7}`. В PostgreSQL для такой ячейки два типа. Оба проверяют, что текст вообще является JSON. Дальше ведут себя по-разному.

| | `json` | `jsonb` |
| --- | --- | --- |
| Как хранит | почти как присланный текст | в разобранном виде |
| Пробелы и порядок ключей | сохраняет | лишние пробелы убирает, порядок ключей не обещает |
| Один ключ написан дважды | оставляет как в тексте | оставляет последнее значение |
| Искать по ключу внутри | неудобно, сначала превращают в `jsonb` | сразу можно, для этого есть индекс GIN |

Ничто не запрещает искать и в `json`. Разница в том, что лежит в ячейке.

`json` хранит присланный текст почти как письмо в конверте: пробелы, порядок ключей и повтор ключа остаются. Чтобы узнать, есть ли внутри `"color": "red"`, база каждый раз заново читает весь текст этой ячейки. Оператора «содержит ли такой кусок» у типа `json` нет. Текст сначала превращают в `jsonb` записью `::jsonb`, и уже у результата спрашивают.

`jsonb` хранит не письмо, а разобранные ключи. Пробелы и исходный порядок пропадают. Зато вопрос «есть ли цвет red» задают сразу, без предварительного чтения всего текста как строки. На такой колонке вечером вешают индекс GIN: поиск идёт по ключам, а не по всей ячейке подряд.

Проверка в `postgres=#`:

```sql
SELECT '{"color": "red"}'::jsonb @> '{"color": "red"}';
```

`@>` значит «левый JSON содержит правый». Ответ будет `t`, то есть да. Та же запись с типом `json` вместо `jsonb` завершится ошибкой: у `json` оператора `@>` нет. Рабочий обходной путь — превратить на лету:

```sql
SELECT '{"color": "red"}'::json::jsonb @> '{"color": "red"}';
```

Для одной строки это незаметно. Для миллиона строк читать и разбирать текст на каждый запрос дорого. Поэтому колонку, внутри которой будут искать, сразу объявляют `jsonb`. `json` оставляют, когда нужно сохранить текст байт в байт таким, каким его прислали.

Это не выбор «менять или не менять». Обе колонки потом можно заменить новой записью. Разница только в хранении: `json` помнит исходный текст, `jsonb` помнит разобранные ключи и поэтому по ним ищут.

Заменяют ячейку целиком одинаково у обоих типов:

```sql
UPDATE products SET attrs = '{"color": "blue"}' WHERE sku = 'SKU-1';
```

Эту команду пока не запускайте: таблицы `products` ещё нет. Ниже только разбор слов.

`UPDATE` — команда «измени уже лежащие строки». `products` — в какой таблице. `SET` — что записать. `attrs` — имя колонки. Знак `=` здесь значит «положи в эту колонку новое значение». `'{"color": "blue"}'` — само новое значение, текст JSON в одинарных кавычках.

`WHERE` — не все строки, а только те, которые подходят под условие. Без `WHERE` команда поменяла бы `attrs` у каждого товара в таблице.

`sku` — имя колонки с артикулом товара. В учебной базе у чайника артикул будет текстом `SKU-1`. `sku = 'SKU-1'` читается так: «артикул равен тексту SKU-1». Слева колонка, справа значение, с которым её сравнивают. Кавычки одинарные, потому что `SKU-1` — текст, не число. Точка с запятой заканчивает команду.

У `jsonb` можно поменять один ключ, не переписывая остальные. `jsonb_set` берёт текущее значение, путь к ключу и новое значение ключа:

```sql
UPDATE products
SET attrs = jsonb_set(attrs, '{color}', '"blue"')
WHERE sku = 'SKU-1';
```

`'{color}'` — какой ключ менять. `'"blue"'` — новое значение, это JSON-строка, поэтому кавычки двойные внутри одинарных. Цвет станет `blue`, остальные ключи в `attrs` останутся.

Готовые строки:

```sql
attrs jsonb NOT NULL DEFAULT '{}'::jsonb
legacy_payload json
```

Первая строка, слово за словом. `attrs` — дополнительные свойства товара, набор заранее не фиксируют. `jsonb` — разобранный JSON. `NOT NULL` — ячейка не бывает пустой в смысле `NULL`. `DEFAULT '{}'::jsonb` — если свойства не передали, запишется пустой объект, то есть «скобки есть, ключей нет».

Кусок `'{}'::jsonb` читают так. `'{}'` — текст из двух скобок. `::jsonb` — «считай этот текст значением типа jsonb». Без `::jsonb` база увидела бы просто текст, а колонке нужен именно JSON.

Вторая. `legacy_payload` — старый кусок JSON, который хранят как прислали. Тип `json`. Ограничений нет: ячейка может быть `NULL`.

Деньги, обязательные поля и ссылки на другие таблицы в JSON не прячут. У обычной колонки есть тип и `CHECK`. У ключа внутри JSON этого нет: туда легко записать и число, и текст, и ничего.

Фраза: «Искать по ключу внутри буду в `jsonb`: он уже разобран, и у него есть оператор `@>`. `json` — если надо сохранить присланный текст как есть. Искать в нём тоже можно, но сначала каждый раз превращают в `jsonb`. Цену и ссылку на клиента оставляю обычными колонками».

## serial и IDENTITY

Обе записи решают одну задачу: номер строки выдаёт сама база, по порядку, 1, потом 2, потом 3. Это не отдельный вид данных вроде `integer`. Это способ сказать «целое, следующее число дай сама».

Старая короткая запись:

```sql
id bigserial PRIMARY KEY
```

`id` — имя колонки. `bigserial` — короткое слово PostgreSQL. Оно само делает три вещи: колонку типа `bigint`, счётчик и правило `DEFAULT`, которое берёт из счётчика следующее число. `PRIMARY KEY` в конце значит: эта колонка главная для поиска строки. Пустой она быть не может, и двух строк с одним и тем же `id` быть не может.

Новая запись, её и называйте, когда таблицу создаёте вы:

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

Каждое слово строки выше. `id` — имя колонки, мы сами его так назвали. `bigint` — большое целое число. `GENERATED ALWAYS AS IDENTITY` — следующее число всегда выдаёт база, руками его обычно не пишут. `PRIMARY KEY` — правило, а не число: по `id` находят ровно одну строку, значение не пустое и не повторяется. Само число 1, 2, 3 появляется из-за `IDENTITY`, а не из-за слов `PRIMARY KEY`.

Запоминают эту фразу переводом, не картинкой из четырёх английских слов. `GENERATED` — «создаётся». `ALWAYS` — «всегда». `AS IDENTITY` — «как личный номер». Вместе: «номер всегда создаёт сама база». На бумаге один раз напишите русскую фразу, под ней английскую. Так она и всплывает на собесе, когда нужно сказать: номер выдаёт база, не человек.

Счётчик и `PRIMARY KEY` не заменяют друг друга. Счётчик в обычной вставке выдаёт 1, потом 2, потом 3, поэтому при обычной работе номера не совпадают. Он не запрещает повтор. Повтор появляется, если номер вставили вручную, счётчик отмотали назад или строки скопировали из другого места. Без `PRIMARY KEY` база такие строки примет: в таблице окажутся два клиента с номером 1. `PRIMARY KEY` как раз отвергает вторую.

Если очень надо записать свой номер в колонку с `ALWAYS`, к вставке добавляют слова `OVERRIDING SYSTEM VALUE`. На учёбе это не нужно. Запомните, что без этих слов свой `id` база отвергнет.

Есть более мягкая форма: `GENERATED BY DEFAULT AS IDENTITY`. Свой номер принять можно. Если его не передали, база даст следующий.

В учебной базе оба способа стоят специально. У клиентов и товаров номер объявлен через `IDENTITY`. У заказов — через `bigserial`, чтобы старая запись тоже была перед глазами.

Фраза: «В старых таблицах увидите `serial`. В новой схеме пишу `bigint GENERATED ALWAYS AS IDENTITY`. Смысл один: целое, следующее значение выдаёт база».

## Ограничения ещё раз, на удалении

В начале файла уже были `NOT NULL`, `DEFAULT`, `UNIQUE`, `CHECK`, `REFERENCES` и `PRIMARY KEY`. Здесь то, что к ним добавляют чаще всего на собесе: что делать с детьми, если удалили родителя.

Родитель — таблица, на которую ссылаются. Клиент родитель для заказа. Заказ родитель для позиции заказа. Ребёнок — таблица, в которой лежит номер родителя.

Три готовые строки:

```sql
customer_id bigint NOT NULL REFERENCES customers (id) ON DELETE RESTRICT
order_id bigint NOT NULL REFERENCES orders (id) ON DELETE CASCADE
product_id integer REFERENCES products (id) ON DELETE SET NULL
```

Общая часть у всех трёх. Имя колонки, тип, слово `REFERENCES`, имя родительской таблицы и в скобках колонка родителя, обычно `id`. Смысл `REFERENCES`: записать можно только такой номер, который у родителя уже есть. Заказ на клиента 999 не запишется, если клиента 999 нет.

Дальше развилка `ON DELETE`, «при удалении родителя».

Первая строка. `customer_id` в заказе. `NOT NULL` — заказ без клиента нельзя. `ON DELETE RESTRICT` — клиента удалить нельзя, пока на него есть хотя бы один заказ. База вернёт ошибку и ничего не сотрёт. Если `ON DELETE` не написать вовсе, будет то же самое, `RESTRICT`.

Вторая. `order_id` в позиции заказа. `ON DELETE CASCADE` — вместе с заказом удалятся и его позиции. Позиция без заказа не нужна, поэтому каскад здесь уместен.

Третья. `product_id` в позиции. `NOT NULL` нет специально. `ON DELETE SET NULL` — товар удалили, в позиции номер товара становится `NULL`, сама позиция остаётся. Пустое значение должно помещаться, поэтому `NOT NULL` здесь писать нельзя: правила противоречили бы друг другу.

`ON DELETE CASCADE` на клиента, у которого есть заказы, первым вариантом не предлагают. Каскад сотрёт заказы и историю покупок.

Имя у ограничения нужно, когда его потом будут удалять или менять. Без имени база имя придумает сама, и его придётся искать.

```sql
CONSTRAINT orders_status_check CHECK (status IN ('new', 'paid', 'cancelled'))
```

Каждое слово строки выше: `CONSTRAINT` — «дальше идёт имя правила». `orders_status_check` — это имя, его придумали мы. `CHECK` — правило. `status IN ('new', 'paid', 'cancelled')` — значение `status` обязано быть одним из трёх текстов. `IN` значит «входит в список». Тексты в одинарных кавычках.

Фраза: «Ссылка — это `REFERENCES`. `RESTRICT` не даёт удалить родителя, пока есть дети. `CASCADE` удаляет детей вместе с ним. `SET NULL` обнуляет ссылку, и тогда колонка без `NOT NULL`».

## ALTER TABLE

`CREATE TABLE` делает таблицу. `ALTER TABLE` меняет уже существующую. Имя таблицы пишут сразу после `ALTER TABLE`, потом действие.

Добавить колонку:

```sql
ALTER TABLE customers ADD COLUMN nickname text;
```

`customers` — какую таблицу меняем. `ADD COLUMN` — добавить колонку. Дальше обычная строка колонки: имя `nickname`, тип `text`. Других правил нет, псевдоним можно не заполнять.

Удалить колонку:

```sql
ALTER TABLE customers DROP COLUMN nickname;
```

`DROP COLUMN` — убрать колонку. Данные в ней тоже пропадут. Имя колонки после этих слов.

Поменять тип:

```sql
ALTER TABLE customers ALTER COLUMN phone TYPE varchar(80);
```

`ALTER COLUMN` — меняем одну колонку. `phone` — её имя. `TYPE varchar(80)` — новый тип, текст не длиннее 80. Команда пройдёт, только если уже лежащие телефоны влезают в 80 символов. Если какой-то длиннее, база вернёт ошибку и не изменит ничего.

Добавить правило к уже созданной таблице:

```sql
ALTER TABLE products
    ADD CONSTRAINT products_stock_nonnegative CHECK (stock >= 0);
```

Перенос на вторую строку ничего не значит, так просто короче читать. `ADD CONSTRAINT` — добавить именованное правило. Имя — `products_stock_nonnegative`. Само правило — `CHECK (stock >= 0)`, остаток не бывает отрицательным. Если в таблице уже лежит отрицательный остаток, команда не пройдёт.

Удалить таблицу целиком:

```sql
DROP TABLE orders;
```

Пропадёт и форма таблицы, и все строки в ней. На учёбе команду знать. На рабочей базе её не запускают, пока явно не попросили удалить данные.

Фраза: «Новую колонку — `ADD COLUMN`. Убрать — `DROP COLUMN`. Сменить тип — `ALTER COLUMN ... TYPE ...`. Новое правило — `ADD CONSTRAINT`. Уже лежащие данные должны подходить под новый тип и под новое правило, иначе база откажется».

## Что сказать, если попросят таблицу с нуля

Пока пишете, проговаривайте выбор типа, не только имя колонки.

- Главная колонка для поиска строки чаще всего называется `id`: `bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`. Числа 1, 2, 3 даёт `IDENTITY`. `PRIMARY KEY` только запрещает пустое и повтор. В старом стиле то же показывают словом `bigserial`.
- Почта и артикул — `varchar` и `UNIQUE`.
- Имя без потолка длины — `text`.
- Цена — `numeric(12, 2)` и `CHECK (price >= 0)`.
- Переключатель — `boolean NOT NULL DEFAULT true` или `false`.
- Момент создания — `timestamptz NOT NULL DEFAULT now()`.
- Ссылка на другую таблицу — `REFERENCES` и одно из трёх: `RESTRICT`, `CASCADE`, `SET NULL`.
