# Воскресенье. JSON, XML и REST

`json` и `jsonb` в PostgreSQL были в субботу. Здесь другое: текст JSON как формат обмена, рядом с XML, и HTTP-контракт, которым вы уже пользуетесь с фронта.

## Шесть типов JSON

По RFC 8259 значение бывает только одного из шести видов.

| Тип | Как выглядит | Пример |
| --- | --- | --- |
| string | Строка в двойных кавычках, UTF-8 | `"paid"` |
| number | Целое, дробное или с экспонентой, без кавычек | `100`, `3.14`, `1e-5` |
| boolean | Ровно `true` или `false` строчными буквами | `true` |
| array | Упорядоченный список | `["a", "b"]` |
| object | Набор пар «ключ: значение». Ключ — всегда строка | `{"id": 10}` |
| null | Ровно `null` | `null` |

Порядок элементов массива обязателен. Порядок ключей объекта стандарт не гарантирует.

Отдельного типа даты и времени в JSON нет. Момент передают строкой ISO 8601: `"2026-10-25T07:15:00Z"`. Буква `Z` значит UTC.

Отдельного типа для байтов нет. Файл и вообще двоичные данные передают строкой Base64.

В JSON также нет `undefined`, комментариев, одинарных кавычек, висячей запятой и ключа без кавычек. Число одно: стандарт не делит его на int и float. `NaN` и `Infinity` в JSON нельзя. Функцию положить нельзя.

`null` и отсутствующий ключ — разные случаи. `null` значит «поле пришло и оно пустое». Нет ключа — поле не присылали. Для `PATCH` это стоит зафиксировать в контракте: затираем колонку в SQL `NULL` или оставляем старое значение.

Объект JavaScript, с которым вы работаете каждый день, богаче текста JSON. У объекта бывают одинарные кавычки, `undefined`, методы, `Date`, `Map`. `JSON.stringify` превращает `Date` в строку. `JSON.parse` возвращает строку, а не `Date`, пока код сам так не решит. `undefined` в объекте при `JSON.stringify` пропадает, в массиве становится `null`.

В Python тот же текст разбирает `json.loads`: `true` / `false` / `null` становятся `True` / `False` / `None`, объект становится `dict`, массив — `list`.

## JSON и XML

| | JSON | XML |
| --- | --- | --- |
| Структура | Пары «ключ: значение» и списки | Теги, вложенность, атрибуты |
| Объём | Мало служебных символов | Тег пишется дважды: `<name>...</name>` |
| Схема | JSON Schema, часто по желанию | XSD и DTD, проверка жёсткая |
| Разбор | Быстрый, в языках есть из коробки | Тяжелее: дерево DOM или потоковый SAX |
| Где привычен | Веб, сервисы, колонка JSONB | Банки, госсектор, SOAP, подпись документа XML-DSig |

XSD (XML Schema Definition) — отдельный XML-документ, который описывает, какие теги разрешены, в каком порядке они вложены, какие у них типы и какие поля обязательны. Проверяющая сторона отвергает файл, если он со схемой не совпал. DTD — более старый и бедный способ описать структуру XML. JSON Schema делает похожую работу для JSON, но во многих внутренних API она необязательна: контракт живущий в коде и в примерах.

Когда берут XML. Внешняя система уже обязала формат: банковский шлюз, факторинг, фискальный документ, обмен вроде СБИС или Диадок, где регулятор или контрагент приложил XSD. Подпись документа тоже часто живёт на XML. В этом случае «нам удобнее JSON» не аргумент, пока другая сторона не согласилась.

Когда берут JSON. Свой REST, событие между своими сервисами, свободная нагрузка, которую кладут в JSONB. Его проще читать человеку и проще разобрать в JavaScript и Python.

Фраза: «Внутри и для веба — JSON. XML — когда схема жёсткая и её дала другая сторона, чаще банк, государство или подписываемый документ. XSD — это и есть файл с этой схемой».

С фронта честно звучит так: рабочие API были JSON, XML отличите и прочитаете простой документ, своим ежедневным форматом он не был.

## REST

REST здесь — HTTP API вокруг ресурса. Адрес называет объект, метод называет действие. Запрос самодостаточен: всё нужное приходит в нём, сервер не обязан помнить предыдущий вызов, чтобы понять этот.

```text
GET    /orders
POST   /orders
GET    /orders/10
PUT    /orders/10
PATCH  /orders/10
DELETE /orders/10
```

Тело для такого API — JSON. Заголовок: `Content-Type: application/json`.

| Метод | Зачем | Повтор того же запроса |
| --- | --- | --- |
| GET | Прочитать | Состояние не меняет |
| POST | Создать ресурс или запустить действие | Может создать вторую запись |
| PUT | Заменить ресурс по известному адресу целиком | Повтор приводит к тому же состоянию |
| PATCH | Изменить часть полей | Повтор с тем же итоговым телом оставляет тот же результат |
| DELETE | Удалить | Ресурса уже нет, состояние то же |

Идемпотентность: повторный одинаковый запрос не меняет результат ещё раз. `GET`, `PUT` и `DELETE` идемпотентны. `POST` нет, если сервер отдельно не защитился ключом идемпотентности. `PATCH` идемпотентен, когда тело описывает желаемый итог («статус равен paid»), и не идемпотентен, когда тело описывает приращение («прибавь 1»).

Безопасный метод данные не меняет. Из этого списка это `GET`.

Коды группами:

- `2xx` — получилось. `200` есть тело, `201` ресурс создан, `204` тело не нужно.
- `4xx` — проблема запроса. `400` запрос не разобрать, `401` не узнали вызывающего, `403` узнали, но нельзя, `404` нет ресурса, `409` конфликт с текущим состоянием (такой email уже есть), `422` тело разобралось, поля не проходят правила.
- `5xx` — сервер не смог выполнить понятный запрос. `500` без уточнения.

`401` и `403` на собесе различайте явно. «Кто вы» и «вам нельзя» — разные ответы, на фронте от них зависят разные экраны.

Пример, который стыкуется с субботней таблицей:

```http
POST /orders HTTP/1.1
Content-Type: application/json

{"customerId": 1, "totalAmount": 1990.5, "status": "new"}
```

```http
HTTP/1.1 201 Created
Content-Type: application/json

{"id": 10, "customerId": 1, "totalAmount": 1990.5, "status": "new", "createdAt": "2026-10-25T07:15:00Z"}
```

`createdAt` в JSON — строка. В колонке `created_at` это уже `timestamptz`. `totalAmount` в JSON — число, в колонке — `numeric`. Точность денег обеспечивает тип в базе, не тип JSON.

## Коротко вслух

Шесть типов: строка, число, булево, массив, объект, null. Даты нет, её везут строкой ISO 8601. Байтов нет, их везут Base64.

XML тяжелее и обычно со схемой XSD. JSON легче и это обычный формат REST.

`POST` может создать дубль. `PUT` на тот же адрес при повторе оставляет тот же ресурс. `401` — не аутентифицирован, `403` — прав нет, `409` — состояние конфликтует, `201` — создали.
