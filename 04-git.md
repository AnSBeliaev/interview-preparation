# Воскресенье. Git

Это блок целиком с уровня выше, плюс то, чего в том блоке не было и что попросили отдельно: `reset` soft/mixed/hard, `revert`, `reflog`.

Команды ниже написаны по одной в строке. В PowerShell Windows 10 связка `&&` не везде работает, поэтому так и запускайте: следующая строка после того, как прошла предыдущая.

Учебный репозиторий заведите отдельно, не внутри рабочего проекта:

```powershell
cd "C:\Users\User\interview-preparation"
mkdir git-drill
cd git-drill
git init
```

## Три места

| Место | Что это |
| --- | --- |
| Рабочая копия | Файлы на диске |
| Индекс | То, что `git add` отложил в следующий коммит |
| История | Уже созданные коммиты |

`git status` показывает первые два относительно последнего коммита. `git diff` — правка, которая ещё не в индексе. `git diff --staged` — то, что уже войдёт в коммит.

## Хороший коммит

Один коммит закрывает одну правку. Починку бага и переименование половины модуля в один коммит не смешивают: откатить и прочитать такое трудно.

Сообщение по форме Conventional Commits. Префикс говорит вид изменения: `feat`, `fix`, `perf`, `refactor`. В скобках — область. Дальше короткое действие.

Заголовок — до 50 символов, в повелительном наклонении. Вторая строка пустая. Это обязательно: по пустой строке инструменты отделяют заголовок от тела. С третьей строки — зачем сделано, какой побочный эффект, на какую задачу ссылка.

Через редактор: `git commit` без `-m`. Откроется редактор.

```text
feat(dwh): add incremental shop marts

Switched from full refresh to loading by updated_at.
Closes #DWH-402.
```

Через терминал тело передают вторым `-m`:

```powershell
git commit -m "feat(dwh): add incremental shop marts" -m "Switched from full refresh to loading by updated_at. Closes #DWH-402."
```

Первый `-m` становится заголовком, второй — телом, пустую строку между ними Git ставит сам.

Если в команде принят другой шаблон сообщения, на работе пишут его. На собеседовании покажите эту форму и скажите, что в репозитории ляжете на местное правило.

Заголовок из примера короче 50 символов. Длинный заголовок вроде «поправил всё по ревью и ещё заодно формат» как раз то, что эта форма запрещает.

## Конфликт слияния

Конфликт появляется, когда две ветки поменяли одно и то же место и Git не выбирает победителя сам.

Анатомия в файле:

```text
<<<<<<< HEAD
CLICKHOUSE_BUFFER_SIZE = 50000
=======
CLICKHOUSE_BUFFER_SIZE = 100000
>>>>>>> feature/tune-dwh-ingestion
```

`HEAD` — ваша текущая ветка. После `=======` — входящая ветка, здесь `feature/tune-dwh-ingestion`. Маркеры кодом не являются. В файле, который пойдёт в коммит, их остаться не должно.

В терминале:

1. Открыть файл.
2. Оставить нужное значение. Иногда это не «левое или правое», а смесь: одна строка ваша, соседняя из входящей ветки.
3. Удалить строки `<<<<<<<`, `=======`, `>>>>>>>`.
4. Проверить файл. Если в проекте есть тесты, прогнать их (`pytest` — если они есть; ради выходных pytest ставить не нужно).
5. `git add` на файл.
6. `git commit`. Если Git уже открыл сообщение коммита слияния, сохраните его. Отдельный `-m` нужен, только когда коммит не завершился сам.

Пока конфликт не разобран, `git status` пишет `unmerged`. После `git add` путь из этого списка уходит.

Если слияние пошло не туда и коммит слияния ещё не создан:

```powershell
git merge --abort
```

В IDE то же самое называется трёхсторонним слиянием. В VS Code и Cursor слева текущая версия (current / ours), справа входящая (incoming / theirs), в центре результат. В PyCharm то же деление: Local, Incoming, Result.

Кнопки:

- Accept Current / Accept Yours — оставить свою сторону целиком;
- Accept Incoming / Accept Theirs — взять входящую сторону целиком;
- Accept Both — оставить оба куска друг за другом, потом руками убрать лишнее.

Кнопка не освобождает от чтения. После неё в файле не должно остаться маркеров. Дальше те же `git add` и завершение коммита.

## cherry-pick

```powershell
git switch main
git cherry-pick c3a4f12
```

`cherry-pick` берёт изменения одного коммита и заново применяет их на текущей ветке. Получается новый коммит с новым хешем. Сообщение по умолчанию то же. Старый коммит на своей ветке не исчезает.

Зачем. Длинная ветка ещё не готова к слиянию, а один коммит из неё нужен в `main` сейчас.

Учебный случай из старшей методички, его рассказывают как устройство приёма, не как свою биографию. В длинной ветке `feature/new-auction-engine` починили утечку соединений в пуле. Ждать конца всей ветки нельзя, в `main` нужен только фикс:

```powershell
git switch main
git cherry-pick c3a4f12
```

Если то же место на `main` уже другое, cherry-pick останавливается на конфликте. Разбор тот же: маркеры, `git add`, `git cherry-pick --continue`. Бросить попытку: `git cherry-pick --abort`.

## merge и rebase

`git merge` соединяет две истории. Если ветка ушла в сторону, появляется коммит слияния. Хронология и сам факт ветки сохраняются. Так соединяют уже опубликованные и общие ветки.

`git rebase` снимает ваши коммиты и кладёт их сверху на свежий кончик базовой ветки. История получается прямой, без лишнего коммита слияния. Так готовят свою ветку перед pull request, пока её не забрали другие.

```powershell
git switch feature/orders
git rebase main
```

Чужой опубликованный `main` rebase-ом не переписывают. После rebase хеши ваших коммитов другие. Если ветку уже отправили на сервер, обычный `push` не примется, и дальше человек часто тянется к принудительной отправке. На общую ветку так не делают.

Фраза: «Свою ещё не отправленную ветку могу переложить rebase на свежий main. Общую историю соединяю merge».

## reset и revert

Оба умеют «откатить», делают это по-разному.

`git revert <hash>` создаёт новый коммит, который отменяет изменения указанного. История не стирается. Так отменяют коммит, который уже уехал на сервер и мог попасть к другим.

`git reset` двигает указатель ветки. Режим говорит, что сделать с индексом и рабочей копией.

| Команда | Коммит | Индекс | Рабочая копия |
| --- | --- | --- | --- |
| `git reset --soft HEAD~1` | Последний коммит снят с ветки | Правки остаются в индексе | Файлы на месте |
| `git reset HEAD~1` | То же. Это режим `--mixed`, он по умолчанию | Индекс очищен от тех правок | Файлы на месте, как незакоммиченные |
| `git reset --hard HEAD~1` | То же | Приведён к цели | Незакоммиченное и снятый коммит выбрасываются из файлов |

`HEAD~1` — предыдущий коммит. `reset` удобен, пока коммит только ваш и на сервер не уходил. `--hard` уничтожает несохранённую работу. Его не предлагают как способ чинить общий `main`.

Фраза: «Уже отправленное отменяю через `revert`, появляется новый коммит. Неотправленный свой коммит могу снять `reset`. `--soft` оставляет правки в индексе, `--mixed` оставляет их в файлах вне индекса, `--hard` выбрасывает и их».

## reflog

`reset --hard` убирает коммит из ветки, но несколько недель Git помнит, куда указывал `HEAD`. Это местный журнал, не часть общей истории. На сервер он не уезжает. По нему возвращают коммит, который «пропал» из `git log`.

```powershell
git reflog
git reset --hard HEAD@{1}
```

`git reflog` показывает строки вида `HEAD@{0}`, `HEAD@{1}`: куда голова переходила. Находите хеш нужного коммита или запись до плохого reset и делаете `git reset --hard` уже на него. После этого коммит снова в `git log`.

Если прошло много времени или журнал чистили, записи может не быть. Пока выходные и вы только что снесли коммит в учебном репозитории, `HEAD@{1}` обычно и есть «как было до reset». Смотрите хеш глазами, не сбрасывайтесь на первую строку вслепую: `HEAD@{0}` — это текущее, уже плохое состояние.

## Прогон на 25 минут

В `git-drill`. Обе ветки меняют одну и ту же строку, иначе Git сольёт файл сам и конфликта не будет. Сразу после первого коммита ветка переименовывается в `main`: у части установок первая ветка называется `master`.

```powershell
git init
Set-Content -Path config.txt -Encoding ascii -Value "size = 50000"
git add config.txt
git commit -m "feat(config): set buffer size" -m "Initial buffer for local drills."
git branch -M main
git switch -c feature/tune-dwh-ingestion
Set-Content -Path config.txt -Encoding ascii -Value "size = 100000"
git add config.txt
git commit -m "feat(config): raise buffer size" -m "Twice the buffer on the feature branch."
git switch main
Set-Content -Path config.txt -Encoding ascii -Value "size = 75000"
git add config.txt
git commit -m "feat(config): tune buffer on main" -m "Main moved the same line the feature branch edits."
git merge feature/tune-dwh-ingestion
```

В `config.txt` появятся маркеры вокруг `75000` и `100000`. Оставьте `size = 100000`, маркеры удалите, затем:

```powershell
git add config.txt
git commit -m "merge: keep feature buffer size"
```

Потом отдельный коммит только на ветке и перенос его в `main`:

```powershell
git switch feature/tune-dwh-ingestion
Add-Content -Path config.txt -Encoding ascii -Value "retry = 3"
git add config.txt
git commit -m "fix(config): retry ingest three times" -m "Short retry so a blip does not drop the batch."
git log --oneline -1
git switch main
git cherry-pick ВСТАВЬТЕ_ХЕШ
```

Хеш берите из вывода `git log`, не из методички. В файле на `main` должна появиться строка `retry = 3`.

Откат этого переноса новым коммитом:

```powershell
git revert HEAD
```

Потеря и возврат коммита. Только в `git-drill`. Сначала запомните хеш текущего коммита из `git log --oneline -1`, потом:

```powershell
git reset --hard HEAD~1
git log --oneline -3
git reflog
git reset --hard HEAD@{1}
```

`git log` после второго reset снова показывает коммит, который `--hard` убрал из ветки. Если `HEAD@{1}` уже не он, берите из reflog хеш, который записали до `--hard`. `--soft` в этом прогоне не нужен: его отличие от `--hard` вы уже можете показать на словах, файлы при `--soft` остаются.

К концу прогона без заметок говорите: чем merge отличается от rebase, что делает cherry-pick, чем `--soft` отличается от `--hard`, зачем revert на уже отправленном коммите, куда смотреть после неудачного reset.
