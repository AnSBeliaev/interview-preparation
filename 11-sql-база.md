# Понедельник. SQL, базовый блок

2–3 часа, первым. Контейнер `pgstat`, не субботний `pg`. Таблица заказов здесь уже есть, у неё колонки `user_id` и `amount`. В магазине из [03-sql-запросы.md](03-sql-запросы.md) те же вещи называются `customer_id` и `total_amount`. Запросы оттуда в этот контейнер не копируют.

Консоль:

```powershell
docker start pgstat
docker exec -it pgstat psql -U postgres
```

Внутри `psql` описание заказа: `\d orders`. Выход: `\q`.

Четыре задачи в конце файла решаются без подсказок. Ответов под ними нет.

## 1. Вторая таблица для JOIN

Заказы лежат в `orders`. Почты и города там нет: в заказе записан только номер пользователя, колонка `user_id`. Чтобы в одной строке ответа увидеть и сумму заказа, и имя человека, нужна вторая таблица. Её имя — `users`. `JOIN` потом поставит строку заказа рядом со строкой пользователя, у которого тот же номер.

Этот шаг таблицу `orders` не трогает. Сначала появляется пустая `users`, потом в неё добавляются строки.

### Создать таблицу

`CREATE TABLE` задаёт колонки. Строк с людьми после этой команды ещё нет. База ответит `CREATE TABLE`.

```sql
CREATE TABLE users (
  id int PRIMARY KEY,
  name varchar(100) NOT NULL,
  email text UNIQUE,
  city text,
  is_active boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

Колонки по словам.

- `id int PRIMARY KEY` — номер пользователя, обычное целое. `PRIMARY KEY` значит: номер обязателен и у двух людей не повторяется.
- `name varchar(100) NOT NULL` — имя, не длиннее 100 символов. `NOT NULL` значит: пустым имя не бывает.
- `email text UNIQUE` — почта, длина заранее не ограничена. `UNIQUE` значит: двух одинаковых почт не будет. `NOT NULL` здесь нет, почту можно не указать.
- `city text` — город. Можно не указать.
- `is_active boolean NOT NULL DEFAULT true` — человек активен или нет. Если при добавлении строки это поле не передали, база сама запишет `true`.
- `created_at timestamptz NOT NULL DEFAULT now()` — момент создания. Если его не передали, база подставит текущее время.

Номер в этой таблице не выдаётся сам. В магазине из субботы номер делал `IDENTITY`. Здесь номер каждый раз приходит в команде `INSERT`, потому что числа `0`, `1`, `2` уже заготовлены ниже.

### Добавить много строк одной командой

`INSERT INTO` добавляет строки в таблицу, которая уже создана. Колонки в скобках — куда писать. `SELECT` ниже собирает готовые строки, и `INSERT` записывает их в `users`.

```sql
INSERT INTO users (id, name, email, city)
SELECT g, 'user_' || g, 'user_' || g || '@mail.ru',
       (ARRAY['Москва','Ростов','Казань', NULL])[1 + floor(random()*4)::int]
FROM generate_series(0, 10000) g;
```

`generate_series(0, 10000)` делает числа от 0 до 10000 включительно, каждое число отдельной строкой. Это 10001 число: ноль тоже считается.

Буква `g` в конце строки, после `generate_series(0, 10000)`, даёт этому числу имя. Без имени база выдала бы колонку, к которой нельзя обратиться. Имя можно выбрать любое. Здесь оно короткое: `g`. Во всех трёх первых выражениях `SELECT` эта буква значит «число текущей строки».

На строке, где число равно 15, выражения читаются так.

- `g` — само число `15`. Оно запишется в `id`.
- `'user_' || g` — текст `user_`, знак `||` приклеивает к нему число. Получается `user_15`. Это имя.
- `'user_' || g || '@mail.ru'` — к `user_15` тем же знаком приклеивается `@mail.ru`. Получается почта `user_15@mail.ru`.

На следующей строке `g` уже другое число, поэтому имя и почта тоже другие. Одна и та же буква стоит в трёх местах, потому что номер, имя и почта строятся из одного и того же числа.

Четыре выражения в `SELECT` попадают в четыре колонки слева направо.

| Куда | Откуда | При `g = 15` |
| --- | --- | --- |
| `id` | `g` | `15` |
| `name` | `'user_' \|\| g` | `user_15` |
| `email` | `'user_' \|\| g \|\| '@mail.ru'` | `user_15@mail.ru` |
| `city` | элемент списка городов | один из четырёх вариантов |

Знак `||` склеивает текст и число в одну строку.

Город выбирается заново для каждого человека. Список из четырёх клеток:

```sql
ARRAY['Москва','Ростов','Казань', NULL]
```

Первая клетка имеет номер 1: в PostgreSQL отсчёт массива начинается с единицы.

| Номер | Город |
| --- | --- |
| 1 | Москва |
| 2 | Ростов |
| 3 | Казань |
| 4 | пусто, `NULL` |

Номер клетки считается так: `1 + floor(random()*4)`. `random()` даёт дробь от 0 до 1, саму единицу не включая. Умножение на 4 растягивает её до промежутка от 0 до 4. `floor` оставляет целую часть: получается 0, 1, 2 или 3. Плюс единица переводит это в номера клеток 1, 2, 3 или 4. Около четверти людей останутся без города. Это нужно дальше, в задании `WHERE city IS NULL`.

`is_active` и `created_at` в списке колонок `INSERT` не названы. База сама поставит `true` и текущее время.

Ответ базы: `INSERT 0 10001`.

Тот же `SELECT` без `INSERT` только печатает строки на экран и в таблицу ничего не пишет. Имеет смысл сначала посмотреть пять строк:

```sql
SELECT g, 'user_' || g
FROM generate_series(0, 4) g;
```

### Два человека без заказов

Для `LEFT JOIN` нужны пользователи, на которых не ссылается ни один заказ. Их номера 20001 и 20002 лежат далеко от ряда 0…10000, чтобы не столкнуться с уже занятым `id`.

```sql
INSERT INTO users (id, name) VALUES (20001, 'no_orders_1'), (20002, 'no_orders_2');
```

`VALUES` перечисляет строки руками. Одна скобка — одна строка. Первое значение внутри скобки идёт в `id`, второе в `name`. Почта и город не переданы, там будет пусто. Ответ базы: `INSERT 0 2`.

Проверка:

```sql
SELECT id, name, email, city FROM users WHERE id IN (0, 15, 20001);
```

## 2. ALTER TABLE

`CREATE TABLE` делает новую таблицу. `ALTER TABLE` меняет таблицу, которая уже есть: добавить колонку, переименовать её, сменить тип, убрать, повесить правило. Строки пользователей при этом не удаляются. Меняется форма таблицы.

Имя таблицы пишут сразу после `ALTER TABLE`. Дальше идёт действие. Каждую команду заканчивают точкой с запятой и запускают отдельно. После неё база отвечает `ALTER TABLE`. Посмотреть, что получилось: `\d users`.

### Добавить колонку

```sql
ALTER TABLE users ADD COLUMN phone varchar(20);
```

- `users` — какую таблицу меняем.
- `ADD COLUMN` — добавить колонку.
- `phone varchar(20)` — её имя и тип. Текст не длиннее 20 символов.

У десяти тысяч уже лежащих людей эта колонка появится пустой, `NULL`. Значение по умолчанию в команде не задано, поэтому база не выдумывает номер телефона.

### Сменить тип

```sql
ALTER TABLE users ALTER COLUMN phone TYPE text;
```

- `ALTER COLUMN` — меняем одну уже существующую колонку.
- `phone` — её имя.
- `TYPE text` — новый тип. `text` — текст без заранее заданного потолка длины.

Команда проходит, только если уже лежащие значения влезают в новый тип. Телефоны сейчас пустые или короткие, поэтому смена с `varchar(20)` на `text` проходит. Если бы новый тип был короче и какой-то телефон в него не влез, база вернула бы ошибку и не изменила ничего.

### Переименовать колонку

```sql
ALTER TABLE users RENAME COLUMN phone TO phone_number;
```

- `RENAME COLUMN` — сменить имя.
- `phone` — старое имя.
- `TO phone_number` — новое имя.

Значения в колонке остаются. Меняется только название. После этой команды имени `phone` в таблице уже нет. Дальше колонку называют `phone_number`.

### Удалить колонку

```sql
ALTER TABLE users DROP COLUMN phone_number;
```

`DROP COLUMN` убирает колонку вместе со всеми телефонами, которые в ней успели оказаться. Остальные колонки, `id`, `name`, `email`, `city`, не трогаются.

Этот кусок специально добавляет колонку и тут же удаляет её, чтобы прошли оба действия. В конце телефона в таблице нет.

### Значение по умолчанию для уже существующей колонки

```sql
ALTER TABLE users ALTER COLUMN city SET DEFAULT 'Москва';
```

- `ALTER COLUMN city` — колонка города.
- `SET DEFAULT 'Москва'` — если в будущем `INSERT` не передаст город, база сама запишет `Москва`.

Уже лежащие пустые города эта команда не заполняет. `DEFAULT` срабатывает только в момент новой вставки, когда значение не пришло. Старые `NULL` в `city` останутся пустыми. Проверка: `\d users` в колонке `city` покажет значение по умолчанию `Москва`.

### Правила на таблице заказов

Дальше две команды для `orders`. Их запускают, когда `\d orders` уже показывает эту таблицу и в ней есть колонки `user_id` и `amount`. Пока таблицы нет, база ответит, что отношения `orders` не существует.

```sql
ALTER TABLE orders ADD CONSTRAINT orders_user_fk FOREIGN KEY (user_id) REFERENCES users (id);
```

- `ADD CONSTRAINT` — добавить именованное правило.
- `orders_user_fk` — имя правила. Его придумали мы, чтобы потом правило можно было найти и снять.
- `FOREIGN KEY (user_id)` — колонка заказа, в которой лежит номер пользователя.
- `REFERENCES users (id)` — этот номер обязан уже существовать в `users.id`.

Заказ на пользователя `15` запишется: такой человек есть. Заказ на номер, которого нет в `users`, база отвергнет целиком.

```sql
ALTER TABLE orders ADD CONSTRAINT amount_positive CHECK (amount >= 0);
```

`CHECK (amount >= 0)` — сумма заказа не бывает отрицательной. Если в таблице уже лежит отрицательная сумма, команда не пройдёт и правило не добавится.

Проверка внешнего ключа. Ожидается ошибка, что пользователя `99999` нет:

```sql
INSERT INTO orders (user_id, amount) VALUES (99999, 10);
```

Если `\d orders` покажет другие обязательные колонки без значения по умолчанию, их тоже нужно перечислить в `INSERT`. Иначе база остановится раньше, на отсутствующем поле, и до проверки номера пользователя дело не дойдёт.

## 3. WHERE

`WHERE` оставляет только те строки, которые проходят условие. Таблицу он не меняет.

Звезда в `SELECT *` значит «все колонки». Для `users` это `id`, `name`, `email`, `city`, `is_active`, `created_at`. Телефона в списке нет: колонку удалили в прошлом разделе. Когда нужны не все колонки, их пишут по именам: `SELECT id, name FROM users`.

### Город и активность сразу

```sql
SELECT * FROM users WHERE city = 'Ростов' AND is_active;
```

`city = 'Ростов'` оставляет жителей Ростова. `AND` требует, чтобы выполнилось и второе условие. `is_active` без сравнения значит `is_active = true`: колонка и так логическая, отдельное `= true` можно не писать. В ответе люди из Ростова, которые активны. Пустой город сюда не попадает.

### Город из списка

```sql
SELECT * FROM users WHERE city IN ('Москва', 'Казань');
```

`IN` проверяет, входит ли город в список. Та же проверка длиннее выглядит так: `city = 'Москва' OR city = 'Казань'`. Жители Ростова и люди без города в ответ не входят.

### Пустой город

```sql
SELECT * FROM users WHERE city IS NULL;
```

`NULL` значит «значения нет». Его ищут словами `IS NULL`. Запись `WHERE city = NULL` не возвращает ни одной строки: сравнение через `=` с пустотой не срабатывает.

### Имя по началу

```sql
SELECT * FROM users WHERE name LIKE 'user_1%';
```

`LIKE` сравнивает текст с образцом. `user_1` — обязательное начало. Знак `%` значит «дальше любые символы». Подходит `user_1`, `user_15`, `user_10000`. Не подходит `user_2`: после `user_` там не единица. Имена `no_orders_1` и `no_orders_2` тоже не подходят.

## 4. BETWEEN

Обе границы входят в диапазон.

```sql
SELECT * FROM orders WHERE amount BETWEEN 100 AND 200;
```

Ловушка с датой. У `timestamptz` полночь — это начало дня. Такой диапазон теряет весь день 31 января после `00:00`:

```sql
WHERE created_at BETWEEN '2026-01-01' AND '2026-01-31'
```

День 31 января целиком попадает сюда:

```sql
WHERE created_at >= '2026-01-01' AND created_at < '2026-02-01'
```

## 5. ORDER BY

```sql
SELECT * FROM orders ORDER BY amount DESC LIMIT 10;
SELECT * FROM users ORDER BY city NULLS LAST, name;
```

`DESC` ставит большие суммы сверху. `LIMIT 10` оставляет десять первых после сортировки. `NULLS LAST` отправляет пустой город в конец. Вторая колонка `name` сортирует людей внутри одного города.

## 6. JOIN

`JOIN` и `INNER JOIN` — одно и то же. В ответе только пары.

```sql
SELECT u.name, o.amount
FROM users u
JOIN orders o ON o.user_id = u.id
LIMIT 10;
```

`LEFT JOIN` оставляет всех пользователей. У кого заказа нет, колонки заказа пустые. Условие `o.id IS NULL` после соединения оставляет только таких:

```sql
SELECT u.id, u.name
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;
```

В ответе будут `20001` и `20002`.

`RIGHT JOIN` сохраняет правую таблицу. На практике его почти не пишут: таблицы меняют местами и пишут `LEFT JOIN`. `FULL JOIN` оставляет строки с обеих сторон. `CROSS JOIN` клеит каждую строку левой таблицы с каждой строкой правой, условия `ON` нет. Его достаточно назвать.

## 7. GROUP BY и HAVING

```sql
SELECT status, count(*), sum(amount), avg(amount)
FROM orders
GROUP BY status;
```

```sql
SELECT u.city, count(o.id) AS orders_count
FROM users u
JOIN orders o ON o.user_id = u.id
GROUP BY u.city
HAVING count(o.id) > 200000
ORDER BY orders_count DESC;
```

`WHERE` выкидывает строки до группировки. `HAVING` выкидывает уже готовые группы. Всё, что в `SELECT` написано без `count`, `sum` или `avg`, должно стоять в `GROUP BY`. Здесь это `status` и `u.city`.

## 8. Порядок выполнения

`FROM` → `JOIN` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY` → `LIMIT`

База собирает строки до `SELECT`. Псевдоним из `SELECT` в `WHERE` ещё не существует. В `ORDER BY` он уже есть: сортировка идёт после `SELECT`.
