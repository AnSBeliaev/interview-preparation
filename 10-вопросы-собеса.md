# Вопросы с собеседования

Ответы своими словами, на уровне junior. Магазин тот же: `customers`, `products`, `orders`, `order_items`.

## 1. Оптимизация

`pg_stats` не устанавливают. Это готовое представление PostgreSQL. По каждой колонке там лежит, сколько разных значений, какие самые частые и сколько пустых. Планировщик смотрит сюда, когда выбирает: читать таблицу целиком или идти в индекс.

Наполняет это представление команда `ANALYZE`. Её не путать с `EXPLAIN ANALYZE`.

```sql
ANALYZE orders;
```

Обычно статистику обновляет autovacuum. Вручную `ANALYZE` запускают, если в таблицу только что залили много строк и план стал странным: база ожидала 10 строк, а прочитала 100000.

Если говорят «установить», чаще имеют в виду расширение `pg_stat_statements`. Оно считает, какие запросы сколько раз выполнялись и сколько времени заняли. Его подключают в конфиге PostgreSQL и создают так:

```sql
CREATE EXTENSION pg_stat_statements;
```

Оптимизировать начинают с медленного запроса, не с пустой базы. Сначала смотрят план, потом решают, нужен ли индекс.

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 1;
```

`EXPLAIN` только показывает план и запрос не выполняет. `EXPLAIN ANALYZE` выполняет запрос и пишет фактическое время и число строк. Смотрят, совпала ли оценка числа строк с фактом и есть ли `Seq Scan` по большой таблице там, где условие отсекает мало строк.

Индексы, которые надо назвать: B-tree и GIN.

B-tree стоит по умолчанию. Он обслуживает равенство, диапазон, сортировку и префикс `LIKE 'abc%'`. Ведущий `%` в `LIKE '%чай'` по нему не ищется. Индекс не вешают на флаг, который почти у всех `true`: он ничего не отсекает, планировщик читает таблицу.

GIN по `jsonb` ищет ключ внутри документа. Оператор `@>`.

```sql
CREATE INDEX orders_customer_id_idx ON orders (customer_id);
CREATE INDEX products_attrs_gin ON products USING gin (attrs);
```

Дополнительные цифры для решения:

- время и фактическое число строк из `EXPLAIN ANALYZE`;
- расхождение оценки и факта, его причина часто в устаревшем `pg_stats`;
- число вызовов и среднее время запроса из `pg_stat_statements`;
- сколько раз таблицу читали целиком и сколько раз по индексу.

Фраза: «Сначала `EXPLAIN ANALYZE` на медленном запросе. Если условие отсекает мало строк, а плана по индексу нет, добавляю B-tree. Для ключа внутри JSONB — GIN. Статистику для плана берёт `pg_stats`, её обновляет `ANALYZE`».

## ETL и ELT

ETL забирает данные, преобразует их отдельным скриптом и в базу кладёт уже готовый результат. Так делают, когда сырьё грязное или персональные данные нельзя грузить как есть.

ELT сначала кладёт сырьё в хранилище, потом преобразует его SQL уже внутри. Так делают, когда само хранилище считает большой объём быстрее внешнего скрипта.

Фраза: «ETL меняет до загрузки. ELT сначала грузит сырьё, потом меняет его SQL внутри хранилища».

## 2. Git

Обычный коммит:

```powershell
git add .
git commit -m "feat: add paid orders query"
```

Длинный комментарий — это заголовок, пустая строка и текст. Заголовок до 50 символов. Второй `-m` становится телом, пустую строку Git ставит сам.

```powershell
git commit -m "feat: add paid orders query" -m "Join orders to customers and keep only paid rows."
```

Без `-m` откроется редактор. Первая строка — заголовок, затем пустая строка, затем пояснение, зачем сделано.

Конфликт возникает, когда две ветки поменяли одни и те же строки. В файле появляются маркеры. До `=======` текущая ветка, после него входящая. Маркеры удаляют, оставляют нужный текст, затем `git add` и `git commit`.

В WebStorm и PhpStorm это окно Merge. Слева текущая ветка, справа входящая, по центру итог. Стрелками переносят куски в центр и нажимают Apply. Файл становится resolved, после этого коммит.

Фраза: «Коммит: `git add`, потом `git commit`. Длинное сообщение — заголовок и тело через второй `-m`. В конфликте убираю маркеры, оставляю нужные строки, делаю `git add` и коммит. В PhpStorm то же самое в окне Merge: слева своё, справа входящее, по центру итог».

## 3. WebSocket и gRPC

WebSocket — постоянное соединение браузера с сервером. Обе стороны шлют сообщения в любой момент. Берут для чата, уведомлений, живого обновления экрана. Сообщения чаще в JSON.

gRPC — вызов метода другого сервиса по контракту в файле `.proto`. Данные бинарные, соединение по HTTP/2. Берут между бэкендами, когда много вызовов и важна схема. Браузер напрямую им обычно не пользуется.

Фраза: «Браузеру для живого потока — WebSocket. Между сервисами со строгим контрактом — gRPC».

## 4. JSON, XML и типы

JSON — обычный формат веба и своих API. XML оставляют, когда формат уже навязан другой стороной: банк, государство, подписываемый документ. Описание разрешённых тегов XML лежит в XSD.

Тип данных говорит, какое значение лежит в поле и что с ним можно делать. У JSON шесть типов: строка, число, логическое, массив, объект и `null`. Отдельного типа «дата» нет, дату передают строкой `2026-10-26`. Отдельного типа «файл» нет, байты передают строкой Base64. В XML типы задаёт XSD: строка, число, дата.

Фраза: «Свой API — JSON. XML, когда схему дала другая сторона, эта схема называется XSD. В JSON шесть типов, даты и байтов среди них нет».

## 5. Второй этап. JOIN

`JOIN` и `INNER JOIN` — одно и то же. В ответе только пары, где условие `ON` сошлось. На данных магазина это два заказа Анны и один Бориса. Клиент `no-orders@example.com` пропадает.

`LEFT JOIN` оставляет каждую строку левой таблицы, той, что написана в `FROM`. Пары нет — колонки правой таблицы пустые, `NULL`. Слева `customers`, поэтому клиент без заказов остаётся.

`RIGHT JOIN` оставляет правую таблицу, ту, что после слова `JOIN`. Тот же смысл почти всегда пишут как `LEFT JOIN`, поменяв таблицы местами.

`FULL JOIN` оставляет обе стороны. Нет пары слева — пустые левые колонки. Нет пары справа — пустые правые. Заказа без клиента в этой схеме нет: у `customer_id` стоит `NOT NULL`.

`CROSS JOIN` клеит каждую строку левой таблицы с каждой строкой правой. Условия `ON` нет. 3 клиента и 3 заказа дают 9 строк.

`ON` — ключевое слово, не оператор. Оно открывает условие склейки. Оператор внутри условия — знак `=`, например `o.customer_id = c.id`.

Фраза: «`JOIN` оставляет только пары. `LEFT` сохраняет левую таблицу, `RIGHT` правую, `FULL` обе. Где пары нет, колонки этой стороны приходят `NULL`. `CROSS JOIN` соединяет все со всеми и `ON` не использует. Писать достаточно `JOIN` и `LEFT JOIN`».
