# Индексы

Текст для человека, который бэкенд раньше не писал. Магазин тот же: клиенты, товары, заказы. На собеседовании из всего про индексы спрашивают то, что разобрано ниже.

## Зачем это вообще

Таблица — это список строк. Заказы лежат друг за другом: первый, второй, третий.

Запрос «найди заказы клиента 1» без дополнительной помощи читает список с начала до конца. На трёх заказах это мгновенно. На миллионе заказов база просматривает миллион строк, чтобы оставить две.

Индекс — второй список, специально для поиска. В нём не вся строка заказа, а пара: значение, по которому ищут, и место строки в таблице. Для заказов по клиенту это выглядит как оглавление.

| Номер клиента | Где лежит заказ |
| --- | --- |
| 1 | заказ 1 |
| 1 | заказ 2 |
| 2 | заказ 3 |

База открывает оглавление, видит «клиент 1 — вот эти два места» и читает только их. Остальные заказы она не просматривает.

Сама строка заказа при этом никуда не переезжает. Индекс её не заменяет. Это дополнительный список рядом с таблицей.

За список приходится платить. Новый заказ нужно записать и в таблицу, и в оглавление. Изменение номера клиента обновляет и то и другое. Поэтому индекс заводят не на всякую колонку, а на ту, по которой часто ищут и которая отбрасывает много лишних строк.

## Когда индекс помогает, а когда нет

Помогает, если из большой таблицы нужна маленькая часть.

Миллион заказов, запрос «заказы клиента 1», а у этого клиента их десять. Оглавление сразу показывает десять мест. Читать миллион не нужно.

Не помогает, если условие почти ничего не отбрасывает.

У всех клиентов код страны `RU`. Запрос «все, у кого код `RU`» возвращает почти всю таблицу. Оглавление по коду страны бесполезно: база всё равно прочитает почти всех. Так же бесполезен флаг `is_active`, если почти все клиенты активны.

Не помогает на крошечной таблице. Три заказа быстрее прочитать подряд, чем открывать отдельный список.

Фраза: «Индекс — отдельный список для поиска. Вешаю его, когда таблица большая, а условие оставляет мало строк. На колонку, где почти все значения одинаковые, не вешаю».

## Что уже создано само

Первичный ключ сам создаёт индекс. В таблице клиентов это колонка `id`. По номеру клиента база ищет через этот список, отдельно писать `CREATE INDEX` для `id` не нужно.

`UNIQUE` тоже сам создаёт индекс. Почта клиента уникальна, поэтому список для поиска по `email` уже есть.

Внешний ключ индекс сам не создаёт. В заказе колонка `customer_id` ссылается на клиента, но отдельного оглавления по ней нет. Соединение заказов с клиентами и поиск «все заказы этого человека» как раз ходят по `customer_id`. На большой таблице этот индекс добавляют руками.

## Как написать команду

```sql
CREATE INDEX orders_customer_id_idx ON orders (customer_id);
```

По словам.

- `CREATE INDEX` — создать список для поиска.
- `orders_customer_id_idx` — имя списка. Его придумали мы, чтобы потом список можно было найти и удалить. На работу поиска имя не влияет.
- `ON orders` — на какой таблице.
- `(customer_id)` — по какой колонке строить список. В скобках имя колонки таблицы `orders`. Самой команды `WHERE` или `JOIN` здесь нет. Эту колонку потом пишут в других запросах: `WHERE customer_id = 1` или `ON o.customer_id = c.id`. Список как раз для таких поисков.

Вид индекса в этой команде не указан. База сама выбирает обычный вид, он называется B-tree. Это вид по умолчанию.

## B-tree

B-tree — обычный индекс. Его берут для числа, текста, даты. На собеседовании для такого поиска называют именно его.

Он ускоряет такие условия.

- Равенство: `WHERE customer_id = 1`, `WHERE email = 'anna@example.com'`.
- Сравнение и диапазон: `WHERE price > 300`, `WHERE price BETWEEN 100 AND 200`.
- Список: `WHERE city IN ('Москва', 'Казань')`.
- Сортировку, если `ORDER BY` названа та же колонка, что в скобках индекса. Индекс по `price` уже лежит по возрастанию цены. Запрос `ORDER BY price` читает этот список по порядку и отдельно ничего не сортирует. Индекс по `price` не помогает запросу `ORDER BY title`: название в этом списке не упорядочено.
- Начало текста: `WHERE name LIKE 'user_1%'`. Знак `%` стоит в конце, начало `user_1` известно, по нему можно искать в оглавлении.

Индекс не помогает запросу, который ищет конец текста.

```sql
WHERE name LIKE '%чай'
```

`%` в начале значит «перед словом `чай` может быть что угодно». Подходит и `чай`, и `горячий чай`. Оглавление индекса разложено по началу строки, как словарь с буквы «а». Открыть его сразу на слове `чай` нельзя: неизвестно, с какой буквы имя начинается. База читает все имена подряд.

Индекс не помогает запросу, который сначала изменяет колонку.

Список построен по почте как она записана: `anna@example.com`. Запрос ниже ищет не эту запись, а почту после функции `lower`, которая приводит буквы к маленьким:

```sql
WHERE lower(email) = 'anna@example.com'
```

В оглавлении нет отдельной колонки «почта маленькими буквами». Старый список к этому условию не подходит. База снова читает почты в таблице и каждую пропускает через `lower`.

Команду с явным видом пишут так, смысл тот же:

```sql
CREATE INDEX orders_customer_id_idx ON orders USING btree (customer_id);
```

`USING btree` можно не писать. Без него будет тот же B-tree.

## GIN и JSON внутри товара

У товара есть колонка `attrs`. В ней не одно число, а документ:

```json
{"color": "red", "volume_l": 1.7}
```

Тип этой колонки — `jsonb`. Вопрос «найди товары, внутри которых цвет красный» смотрит не на всю ячейку целиком, а на ключ `color` внутри неё.

Обычный B-tree сравнивает значение целиком. Для ключа внутри документа он не подходит. Для этого берут второй вид индекса, GIN.

```sql
CREATE INDEX products_attrs_gin ON products USING gin (attrs);
```

`USING gin` здесь пишут обязательно. Без этих слов получился бы B-tree, и поиск по ключу внутри JSON он не обслужит.

Сам поиск:

```sql
SELECT sku, title
FROM products
WHERE attrs @> '{"color": "red"}';
```

Знак `@>` значит «левый документ содержит правый». На учебном магазине так находится чайник `SKU-1`.

Фраза: «Обычный фильтр, диапазон и сортировка — B-tree. Поиск ключа внутри JSONB — GIN и оператор `@>`».

## Как понять, что база им пользуется

Перед запросом пишут `EXPLAIN`. Запрос не меняет таблицу и не печатает сами заказы. Он печатает способ, которым база собирается их читать.

В запросе нельзя написать «используй индекс». База сама сравнивает способы и берёт тот, что считает дешевле. Индекс на таблице для этого недостаточен. Нужны ещё два условия. Запрос ищет по той колонке, на которой список построен. И строк в таблице много, а условие оставляет мало.

Ниже два ответа, которые уже были на наших базах. Первый — магазин, таблица `orders`, три заказа. Второй — база `pgstat`, таблица `users`, около десяти тысяч строк.

### Чтение подряд, индекс не открывали

Команда в магазине:

```sql
EXPLAIN
SELECT * FROM orders WHERE customer_id = 1;
```

Ответ базы, целиком:

```text
Seq Scan on orders  (cost=0.00..1.04 rows=2 width=82)
  Filter: (customer_id = 1)
```

По строкам.

- `Seq Scan` — читать таблицу подряд, с первой строки до последней. Списка для поиска здесь нет.
- `on orders` — какую таблицу читают.
- `cost=0.00..1.04` — оценка «насколько это дорого» по внутренним единицам базы. Это не миллисекунды. Первое число — цена до первой строки, второе — цена всего чтения. Маленькие числа, потому что заказов три.
- `rows=2` — база думает, что в ответе будет две строки. У Анны как раз два заказа.
- `width=82` — оценка, сколько байт занимает одна строка ответа.
- `Filter: (customer_id = 1)` — условие применили уже во время чтения таблицы. База смотрит каждую строку и оставляет те, где номер клиента равен 1.

Индекса по `customer_id` нет. Первичный ключ у заказа на колонке `id`, это номер заказа, не номер клиента. Поэтому способ и называется `Seq Scan`. Даже если индекс по `customer_id` создать, на трёх строках база может оставить то же чтение подряд: три строки прочитать дешевле, чем открывать оглавление. Это не ошибка. Индекс на маленькой таблице можно не держать, он только замедляет запись.

### Чтение по списку

Команда в базе `pgstat`:

```sql
EXPLAIN
SELECT * FROM users WHERE id = 15;
```

Ответ базы, целиком:

```text
Index Scan using users_pkey on users  (cost=0.29..8.30 rows=1 width=110)
  Index Cond: (id = 15)
```

По строкам.

- `Index Scan` — читать через список для поиска, а не всю таблицу подряд.
- `using users_pkey` — имя списка. Его никто не создавал командой `CREATE INDEX`. Он появился сам, потому что `id` — первичный ключ. `pkey` в имени — от слов primary key.
- `on users` — таблица, из которой потом берут саму строку.
- `cost=0.29..8.30` — та же оценка цены. Числа больше, чем у трёх заказов, потому что пользователей около десяти тысяч. Для одной строки из десяти тысяч это всё равно дешевле, чем читать всех подряд.
- `rows=1` — база ждёт одну строку. Номер `id` уникальный, второй пятнадцатый пользователь невозможен.
- `width=110` — оценка размера одной строки ответа, в байтах.
- `Index Cond: (id = 15)` — условие применили внутри списка. `Cond` — сокращение от condition, «условие». База открыла оглавление на значении 15 и пошла сразу к этой строке.

Слово `Filter` здесь не появилось. Условие отработало в индексе, отдельный просмотр всех строк не понадобился.

## Что сказать, если попросят своими словами

Индекс — отдельный список для поиска, строку в таблице он не заменяет. Первичный ключ и уникальная почта такой список уже имеют. Колонка `customer_id` в заказах его сама не получает, на большой таблице я создам его командой `CREATE INDEX`.

Обычные условия и сортировка — вид B-tree, он стоит по умолчанию. Ключ внутри JSON — вид GIN, в команде пишут `USING gin`, ищут оператором `@>`.

Вешаю индекс, когда строк много, а условие оставляет мало. Не вешаю, когда почти все строки и так подходят под условие.
